# Experimental county-derived random-point model implementation plan

> Execute with a subagent, as explicitly requested by the user on November 17, 2026. Use the existing execution/test/verification practices; the user's instruction to plan and execute is authorization to proceed without another approval step.

**Goal:** Deliver a reproducible experimental baseline that learns from randomly allocated locations derived from real historical county outage observations, with a usable CPU artifact and explicit assumptions. The demo is in two days.

**Architecture:** An isolated `outage_model.experimental` workflow ingests real county history, generates reproducible spatial proxy labels, trains a small native LightGBM baseline, and reports results on held-out county/date groups. Its artifacts and outputs remain separate from the strict observed-incident model and probability-release namespace. Existing live weather and frontend behavior are preserved.

**Spec:** The user explicitly accepts training on randomly sampled within-county locations, provided the assumptions are documented. This supersedes the earlier ban on synthetic training labels for this explicitly experimental workflow only. Real county measurements must remain distinguishable from generated point locations and labels.

**Tech stack:** Existing Python 3.12, NumPy, SciPy, PyArrow, Shapely, PyProj, LightGBM/scikit-learn dependencies; reuse installed tools and avoid a second environment/image.

## Global constraints and decisions

- Keep changes in `power_outage_model/`; preserve unrelated edits, existing training package, raster pipeline and strict release gates.
- Hard local storage ceiling: 10,000,000,000 bytes across the model directory; prefer 5 GB when feasible. Existing files already exceed the preferred target. Inventory current bytes before downloads; do not delete existing user files. Stream compressed data and aggregate it instead of storing/extracting a national archive twice. Respect safety headroom and stop before exceeding the hard ceiling.
- Obtain actual historical county records, preferably EAGLE-I's official archive. The prior current-map point samples are not historical county training data. Verify access and small samples before a bulk transfer. No invented county totals, fake dates, guessed missing zeros, or fixtures presented as real fitting.
- County counts measure customers/meters reported without power, not incident counts, new onsets, unplanned classifications or failed-equipment locations. The new target is explicitly **simulated spatial allocation of reported county outage impact**, not verified incident occurrence.
- Explicitly version how count maps to proxy multiplicity/weights. Bound sampled locations (default at most 32 per county-window), conserve the reported customer mass using weights, and never allocate one physical incident per customer. Uniform sampling over verified county analysis land is the default assumption; if only county polygons are available, name that different support explicitly and do not quietly sample ocean as land.
- Use a fixed seed 42 with stable per-county/date/window seeds independent of row order. Save county/date/source identity, original count, point weight and sampling-policy version for each proxy. Preserve source coverage/missingness. Background/absence labels generated by allocation are also simulated, never observed negative incidents.
- Split real parent county/date/weather-event groups **before generating points**. Keep every proxy from the same parent record and overlapping target period on one side of a split. Use chronological later dates, sufficient embargo for any 72-hour overlapping windows, and a separate county holdout where support permits. Do not use a random point split.
- Freeze one generation policy/seed for fitting; report sensitivity under additional fixed seeds. Clearly separate held-out real county aggregate performance from held-out simulated point-label agreement. Point agreement is not validation of actual incident locations; county measurements alone do not establish such accuracy.
- Select only predictors whose data actually exist for training and inference. Current downloaded DWD forecasts cover 2026 and cannot be paired with 2014–2022 outage labels as if historical forecasts. A calendar/geography baseline is acceptable for the deadline; state explicitly if it learns no weather effects. Historical observed/reanalysis weather or later-vintage canopy must be explicitly marked retrospective and cannot be represented as an operational forecast backtest. Do not spend the deadline downloading national multi-year weather if a bounded baseline is feasible without it.
- Use native LightGBM serialization or transparent logistic coefficients, immutable hashes, feature order, seed, environment and source/assumption manifests. Persist the actual trained model, evaluation report, and small representative predictions if real history is accessible. No runtime fitting, implicit fixture fallback, or external/cloud deployment.
- All metadata and inference responses must retain `experimental=true`, `locations_simulated=true`, the count/weight interpretation, source coverage and model ID. A classifier probability is agreement with the allocation policy, never a calibrated physical-outage/household probability. Prefer an explicitly named allocated-impact output where that matches the fit.
- A source-access failure is a data blocker, not permission to synthesize county history. Still finish the executable workflow and exact retrieval instructions; report clearly what actually trained and what did not. Try legitimate public read-only mirrors/official published links before declaring access blocked; never fabricate access or bypass authentication.

- `validation/experimental-point-status.json` and `.md`: actual source access, file sizes, training rows/date/geographic coverage, selected features, fit/check results, real-vs-simulated provenance, limitations and final storage.
- Update `README.md`/package-data discovery only as necessary to expose the isolated workflow. Preserve strict `outage_model.cli` behavior.

## Review focus

1. Outage customers mistaken for independent incidents: tests pin mass conservation and target names.
2. Random points leaking parent records across splits: tests pin disjoint parents, temporal overlap purges and county holdouts.
3. All-zero/missing/truncated county feeds: tests reject missing as zero, incomplete transfers and unsupported nationwide claims.
4. Tiny/island/invalid county geometry and boundary cells: tests pin finite bounded sampling, support containment and deterministic failure.
5. Storage exhaustion/access failure: tests pin bounded writes, no partial artifact promotion, explicit source failure and no fixture fallback.
